# Deploying DocuVault

Production topology:

| Piece        | Where                | Notes                                                     |
| ------------ | -------------------- | --------------------------------------------------------- |
| Frontend     | Vercel               | Static Vite build, `client/` as the root directory          |
| Backend API  | Render Web Service   | Node/Express, `server/` as the root directory              |
| File storage | Render Persistent Disk | Mounted at `/var/data`, survives redeploys                |
| Redis        | Render Key Value     | Required — the server will not boot without it             |
| MySQL        | **Aiven** (free tier) | Render has no managed MySQL; TLS is mandatory here        |

> **Cost warning.** Two things force a paid plan. A Render **persistent disk
> cannot be attached to a free service**, and Puppeteer needs a real headless
> Chromium, which will not fit in the 512MB Starter instance. The cheapest
> working configuration is the **`1c-2g`** web service (1 CPU / 2GB, $25/mo) plus
> a 10GB disk ($2.50/mo) plus a 256MB Key Value instance. The Vercel frontend and
> the Aiven MySQL are free.

## 1. Create the MySQL database on Aiven

1. Sign up at <https://aiven.io> and create a **MySQL** service.
   - The free plan is enough to start. Pick the region closest to your Render
     region (`Oregon`).
2. Wait for the service to reach **running**.
3. Open the service and copy these four values — you need all of them in step 3:
   - **Host**
   - **Port**
   - **User**
   - **Password**
   - **Database name**
   - **SSL certificate** (this is the CA cert; you want the `-----BEGIN
     CERTIFICATE-----` block, not the client cert/key)

## 2. Create the Render services

The repository already contains a `render.yaml` blueprint that creates the web
service, the disk and the Redis instance together and wires Redis in
automatically.

1. Go to <https://dashboard.render.com> → **New** → **Blueprint**.
2. Connect the `DocuVault` GitHub repository.
3. Render will show the values it needs you to supply. Fill in:

   | Variable                 | Value                                    |
   | ------------------------ | ---------------------------------------- |
   | `DB_HOST`                | Aiven host                               |
   | `DB_PORT`                | Aiven port                               |
   | `DB_USER`                | Aiven user                               |
   | `DB_PASSWORD`            | Aiven password                           |
   | `DB_NAME`                | Aiven database name                      |
   | `DB_SSL_CA`              | Aiven CA certificate                     |
   | `CLIENT_URL`             | *(leave blank for now — step 4)*        |
   | `SMTP_USER`              | your Gmail address                       |
   | `SMTP_PASSWORD`          | the **new** app password from step 0     |
   | `SMTP_FROM`              | your Gmail address                       |

   `JWT_SECRET`, `HMAC_SECRET` and `EXTERNAL_DB_ENC_KEY` are auto-generated by
   Render (`generateValue: true`) — do not type anything for those.

   `DB_SSL_CA` must be pasted as a **single line** with the line breaks written
   as literal `\n`, like this:

   ```
   -----BEGIN CERTIFICATE-----\nMIIBkTCB+wIJAK...\n-----END CERTIFICATE-----
   ```

4. Click **Apply**.

The first deploy creates the database schema automatically — `render.yaml` sets
`preDeployCommand: npm run migrate`, which runs after the build and before the
service starts. Nothing else is required to get the tables created.

## 3. Create the first admin account

The migration deliberately does **not** seed the five demo accounts from
`schema.sql` — they all share a publicly known password (`Passw0rd!`) and their
email addresses are in your git history, so seeding them would hand five working
logins to anyone who has read the repo. Create one real admin instead.

You can also just do this through the app once it is up (Sign up → promote in the
database), but running the script from your own machine is the clean route:

```powershell
cd C:\Users\HP\Music\DocuVault\server

# point these at your Aiven values
$env:DB_HOST     = "<aiven host>"
$env:DB_PORT     = "<aiven port>"
$env:DB_USER     = "<aiven user>"
$env:DB_PASSWORD = "<aiven password>"
$env:DB_NAME     = "<aiven database>"
$env:DB_SSL      = "true"
$env:DB_SSL_REJECT_UNAUTHORIZED = "true"
$env:DB_SSL_CA   = "-----BEGIN CERTIFICATE-----\nMIIBkTCB...\n-----END CERTIFICATE-----"

$env:ADMIN_EMAIL = "you@yourdomain.com"
$env:ADMIN_PASSWORD = "<a strong password, 12+ characters>"

npm run migrate -- --create-admin
```

Expected output ends with `[admin] Created super_admin you@yourdomain.com` and
`✅ [migrate] Done.`

The script is idempotent — run it again any time and it is a no-op. (It is also
already configured to run on every Render deploy, so this local run is only
needed to create the admin account.)

Then check the Render logs. You want to see:

```
[storage] STORAGE_ROOT is set (persistent disk) — files survive redeploys.
[db] MySQL connection OK
[redis] Connected to …
✅ [server] Running on http://0.0.0.0:10000
```

Verify the API: `https://docuvault-api.onrender.com/api/health` should return
`{"success":true,"message":"API is up."}`

> The first request after a deploy can take ~30s while the free instance spins
> up. It will also spin down after 15 minutes of inactivity, so the first request
> after a quiet period will feel slow. This is normal for the free tier.

## 4. Deploy the frontend to Vercel

1. Go to <https://vercel.com/new> and import the same repository.
2. Set **Root Directory** to `client`. This is the important part — the repo root
   has no buildable app.
3. Framework preset **Vite**. Build command `npm run build`, output `dist`. Both
   should be detected automatically.
4. Deploy.

`client/.env.production` already points `VITE_API_URL` at the backend and
`client/vercel.json` already handles SPA route refreshes, so no other frontend
config is needed.

---

## 5. Point the backend CORS at the Vercel URL

The backend will reject the frontend until you tell it the URL. In the Render
dashboard, edit `docuvault-api` → **Environment** and set:

```
CLIENT_URL=https://yourapp.vercel.app
```

Then redeploy (Environment changes require a restart).

`CLIENT_URL` accepts a **comma-separated list**, which you will want because
every Vercel deploy gets a unique preview subdomain:

```
CLIENT_URL=https://yourapp.vercel.app,https://app.yourdomain.com
```

## Troubleshooting

**`[redis] Cannot reach Redis at …`** — Redis is not set. Check that the
`docuvault-redis` Key Value instance is running and that `REDIS_URL` is populated
on the web service.

**`[db] MySQL connection FAILED`** — almost always TLS. Aiven requires
`DB_SSL=true`, `DB_SSL_REJECT_UNAUTHORIZED=true` and a correct `DB_SSL_CA`. A
malformed CA (real newlines instead of literal `\n`) is the most common cause.

**Frontend loads, every request fails, console shows CORS** — `CLIENT_URL` does
not match the Vercel origin exactly. Watch for `http` vs `https` and for a
trailing slash.

**Generated documents 404 after a redeploy** — `STORAGE_ROOT` is not set, or the
disk is not attached. Check the boot log for the `[storage] STORAGE_ROOT is set`
line.

**Bulk generation never completes** — the BullMQ worker is in-process, so the
service must be at **1 instance**. Do not scale it up while using a disk.

**`Data truncated for column 'action'`** — a stale `audit_logs.action` enum. The
`npm run migrate` script repairs it; running it once is enough.
